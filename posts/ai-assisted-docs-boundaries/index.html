    怎样与 AI 协作写技术文档

    我们都说可以用 AI 写文档。它知道很多东西，也能很快给出一份初稿。不过，这份初稿不能直接发布，最后的取舍和验证仍然要由人来做。

    我最近写 GitHub REST API 的英文 Quickstart 和 Troubleshooting，正好和 AI 来回磨了几轮。它帮我整理材料、补齐结构，也暴露了几个很具体的问题。

    AI 写作的问题

    写这组文档以前，我看了不少官方案例，也把其中值得学习的内容记进自己的知识库。Stripe 的 Quickstart 有一个设计让我印象很深。容易出错的步骤旁边会放一个简短的折叠块，读者不离开当前页面就能处理问题。

    这个设计放在 Stripe 的页面里很好用。等 AI 根据我的笔记生成初稿时，它没有留意到当前项目已经拆成两篇文章。一篇 Quickstart 负责带读者完成第一次请求，另一篇 Troubleshooting 专门处理错误和异常。AI 仍然在 Quickstart 中加入了简短排错，内容和另一篇正文重复了。

    我让它学习知识库里的笔记，它先做的是照搬。哪些结构适合参考，哪些结构会破坏当前页面的分工，还需要人来判断。知识库能给 AI 提供材料，不能替作者决定文档的信息架构。

    它还很容易把检查动作写得过于含糊。Troubleshooting 的初稿里曾经出现这样一句话。

    check the repository owner and name

    这句话看起来给了任务，读者却不知道去哪里看，也不知道怎样判断。后来正文改成了更明确的操作。先在浏览器中打开仓库地址，再把地址中的 owner 和 repository name 与 API Endpoint 逐段比较。名称后面不能带 .git，路径中也不能多出额外层级。每一种不一致都对应一个具体修改。

    技术文档里的检查指令至少要交代检查对象、查看位置、通过标准和下一步动作。只写 check、verify 或 make sure，通常还没有把任务写完。

    真实运行会发现初稿看不到的问题

    文档结构调整以后，我又从头跑了一遍命令。GitHub CLI 示例沿用了 Bash 的反斜杠续行。在 Windows PowerShell 中，这些反斜杠会被当成额外参数，终端返回了下面的错误。

    accepts 1 arg(s), received 5

    AI 写命令时没有处理不同终端的续行差异。单看 Markdown 和官方参数，这条命令似乎没有问题。真正放进 PowerShell，错误才出现。

    正文后来把 GitHub CLI 命令改成了单行。修正后的请求还没有重新运行，因此没有被标成已经验证成功。

    这次运行还遇到了另一个小插曲。curl 经过代理时先显示 200 Connection established，后面才出现 GitHub API 返回的 200 OK。如果只在输出里搜索 200，很容易把代理连接成功当成接口调用成功。最后仍然要继续检查响应来源和 JSON 字段。

    AI 可以很快完成初稿，人还得把流程真实跑一遍。平台语法、代理响应和输出顺序藏在执行过程中，靠文字推断很难全部发现。

    人与 AI 怎样分工

    这次拉锯让我把 AI 放回了一个更合适的位置。AI 参与整理、比较和检查，也可以根据知识库完成初稿。我负责确定任务目标和范围，提供资料与事实边界，决定每个页面负责什么，最后再运行命令、检查结果并完成发布。

    知识库里也需要区分材料的性质。官方文档用来确认产品行为，本地终端记录用来说明某个环境里实际发生过什么，Stripe、Cloudflare、GitHub 和 Docker 的学习笔记用来比较文档结构。没有运行过的认证失败、限流和网络错误继续标为未验证，不能因为官方文档写过就变成自己的测试结果。

    AI 适合扩大检查范围，作者负责最后的判断。参数、版本、命令输出或错误原因找不到依据时，正确的处理是留下缺口，再补资料或运行验证。

    我目前的 checklist

    • 目标读者、主要任务和完成标准是否清楚。
    • 页面之间是否有重复内容。
    • 命令是否适用于标注的平台和终端。
    • 关键动作后是否有可观察结果与继续条件。
    • 版本、示例输出和错误信息是否有资料或运行记录。
    • 官方确认、实际验证和尚未验证是否分开说明。
    • 内部链接、标签页、折叠块和代码围栏是否正常渲染。
    • Vale 和 MkDocs 严格构建是否通过。

    接下来还要留下什么

    这次项目又给我的待办增加了三项。

    1. 继续记录优秀文档的亮点，学习它们使用的词汇、句式和结构。
    2. 保留有代表性的原文和上下文，再从多个案例中找出可以复用的共同点，用来约束 AI 的行为。
    3. 在每次协作以后更新自己的 checklist 和 SOP，把临时判断变成下一次可以直接使用的检查步骤。

    这套方法的写作工具整理在 GitHub 英文文档写作复盘。在这次磨合中，我也整理了两份可以继续复用的协作指令。

    可复制的协作指令

    下面两份指令来自这次项目使用的最终版本。正文保留方法和取舍，长指令放进折叠块，便于按任务取用。

    通用技术文档 AI 协作指令 
    请把这项任务作为一篇可实际执行的技术文档来写。

开始写正文前，先确认：

1. 目标读者是谁；
2. 文档类型是什么；
3. 读者要完成的唯一主要任务是什么；
4. 最小成功结果是什么；
5. 这篇文档与其他页面怎样分工；
6. 哪些内容来自官方资料，哪些已经实际验证，哪些仍未验证。

写作时遵守以下要求：

- 只保留完成主要任务所需的主路径。
- 不要机械复制优秀案例中的所有结构。
- 写入一个模块前，先检查它是否与其他文档重复。
- 每条命令必须可以直接复制执行。
- 明确区分 Windows PowerShell、Command Prompt、macOS 和 Linux 的命令差异。
- 每个关键动作后写出可观察结果和继续条件。
- 不要只写 check、verify 或 make sure。
- 每项检查都要说明检查对象、所在位置、正确值和失败后的动作。
- 对于会决定读者下一步的关键检查，说明去哪里看什么，并写清不同结果分别意味着什么、接下来做什么。
- 示例版本和输出必须来自真实验证，不得自行编造。
- 未实际复现的结果必须明确标注。
- Quickstart 只保留最短成功路径；详细错误处理放入 Troubleshooting，并使用链接连接两篇文档。
- 文末记录资料来源、测试日期、操作系统、工具版本、实测结果和未验证范围。

完成初稿后，再按以下顺序审查：

1. 检查跨页面重复；
2. 检查每条命令是否有明确验收结果；
3. 检查平台兼容性；
4. 检查事实与实际运行记录是否一致；
5. 检查 Markdown 和 MkDocs 渲染；
6. 列出仍需人工运行验证的步骤。
    Troubleshooting 技术文档 AI 协作指令 
    你要与我协作编写一篇 Troubleshooting 技术文档。本文可能涉及软件、硬件、API、命令行工具、Web 产品、集成流程或其他技术系统。

请先判断文档职责、预测合理的问题、与我确认范围，再编写正文。不要看到参考文档后直接模仿它的结构和内容。

我会提供产品或任务说明、相关文档、目标读者、平台和版本、真实运行记录、已知问题、官方资料、输出格式与范围要求。关键材料缺失时，先指出缺少什么，以及它会影响哪些判断。不要自行补造产品行为、错误信息或测试结果。

第一阶段只做分析与范围确认，不写正文。

1. 还原用户从开始操作到完成任务的正常路径。这只用于识别中断点，不直接复制进正文。
2. 从环境、版本、输入、配置、认证、权限、命令语法、文件、网络、依赖、请求、响应、硬件连接、平台差异和产品限制中寻找潜在故障点。
3. 按照真实遇到、主动复现、官方记录、可靠反馈和流程推断的顺序寻找证据。
4. 为候选问题标记 Observed、Tested、Documented、Reported 或 Inferred。不得把 Inferred 写成已经发生或测试的事实。
5. 只收录有明确症状、会影响当前任务、能够提供诊断或恢复动作的问题。

第一阶段输出候选问题表，至少包含症状或错误信息、发生阶段、可能原因、证据类型、建议优先级、是否收录和判断理由。完成后停止，等待范围确认。

第二阶段在范围确认后编写正文。

正文以读者能够看到或搜索到的症状命名。可以使用完整错误信息、状态码、页面提示、指示灯状态、输出缺失、性能异常或连接失败现象。避免使用 Common problems、Configuration issues、Something went wrong 和 Other errors 这类宽泛标题。

一个问题可以根据复杂度包含症状、可能原因、诊断步骤、结果分支、修复或绕过动作、升级条件和返回原任务的位置。不要强迫所有问题使用相同的小标题。

对于会影响下一步的关键检查，说明在哪里查看、查看什么对象或字段、不同结果代表什么，以及每种结果下一步做什么。只有存在唯一预期结果时，才给出固定正确值。

每条命令或关键操作说明适用系统和版本、完整操作、需要观察的结果，以及不同结果对应的动作。不要虚构完整输出。不同平台使用不同语法时分别提供命令。

诊断先确认症状，再检查常见且容易确认的原因。优先执行只读、低风险和可逆操作，最后才执行重置、删除、回滚或重新安装。某个结果已经确定原因时，停止无关分支。互斥方案要说明适用条件和影响。

修复后可以给出简短恢复信号、让读者重试原步骤，或链接回相关 Quickstart。不要为每个问题机械增加 Verify the fix，也不要重复正常路径的完整成功标准。

写作时区分真实观察、主动复现、官方说明和流程推断。保留错误文本的拼写、大小写和标点。不得虚构版本、日志、截图、命令输出和产品行为。证据不足时提出验证方法或询问，不要直接补写结论。

提交前检查：

- 每个问题是否从明确症状出发；
- 标题是否包含读者可能搜索的错误文本或现象；
- 是否误把 FAQ、正常差异或成功输出写成故障；
- 是否与 Quickstart、Guide 或 Reference 重复；
- 关键检查是否说明位置、对象、条件和后续动作；
- 不同结果是否进入明确分支；
- 命令是否准确、完整并适用于标注环境；
- 是否优先使用低风险、可逆的诊断方法；
- 是否把未经验证的推测写成事实；
- 代码块、链接、标题和发布平台语法是否有效。

发现任何一项不满足时，先修改，再提交最终稿。

    为什么还要保留“古法手作”

    AI 已经把整理材料和生成初稿的成本降得很低。真实经验反而更重要了。命令有没有跑过，输出到底长什么样，一条检查能不能让读者继续，这些事情必须有人亲手做完。

    这也是我还要保留“古法手作”的原因。AI 可以加快执行，人要对最后的文档负责。
