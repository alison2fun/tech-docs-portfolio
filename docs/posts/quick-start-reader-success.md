# 怎样写一篇可执行的 Quickstart

一篇 Quick Start 的目标是让读者完成一次成功操作的路径。因此，它的指令必须是可以执行的，结果必须是可观察的。这就要求 Quick Start 文档写清楚：

1. 应该执行什么命令；
2. 得到什么样的结果；
3. 若出错了，该怎么排查；
4. 下一步怎么做。

我们在写 Quickstart 的时候可以定一个标准：让一个第一次接触这项任务的人，沿着文档一直往下做，就能够完成一次真正可验证的成功。

常用的信息架构是：

**Quickstart**

> Goal<br>
> Before you start<br>
> Step 1<br>
> Step 2<br>
> Step 3<br>
> Verify the result<br>
> Next steps

## 先确认文档骨架

首先，要确认文档的骨架，用一连串的动作把一次完整的成功路径串起来。这一连串的动作可以用小标题写出来，特别是包含动作的标题。

例如：

```text
API Key             ×
Get your API Key    ✓
```

这样写有一个好处：读者读一遍目录，就知道要做什么。

## 写清楚每一个关键动作

接下来要看每一个关键动作。执行每一个步骤都可以压缩成一个简单的结构：

1. Action；
2. Observable result；
3. Pass criteria；
4. Next step。

## 把提醒放在问题发生之前

在读者操作的过程中，可能会有需要提醒的地方，也会遇到一些容易出错的情况。

如果遇到需要提醒的地方，提醒就要尽可能放在问题会发生的地方，也就是在触发问题的命令之前进行简短提醒。

## 区分短排错和复杂故障

如果是比较短的排错，只处理当前步骤即可；如果是比较长的排错，就已经偏离了 Quick Start 这篇文档的功能，应该引导读者到 Troubleshooting 文档中寻找解决办法。

## 把拓展内容放在第一次成功之后

### 成功标志

当读者完成第一次成功路径之后，要显示一个成功标志，也就是成功的提示或结果。

### 拓展操作

如果还有其他额外的拓展操作，可以安排在这个明确的成功之后再展开。

### 进阶说明

完成上述内容后，可以增加其他配置说明，或者提供 Reference、Troubleshooting 等进阶页面的链接。

## 判断内容是否应该保留

判断一段内容该不该放进 Quick Start，核心在于：没有它，读者能不能完成第一次成功？

如果可以，这段内容就不应该被塞进 Quick Start 文档。

## Quick Start 检查清单

最后，我会总结出这样一份 Quick Start 检查清单：

1. **目标预期**：开头有没有直接说明最终会得到什么，让读者知道现在在做什么？
2. **前置条件**：是否让读者知道自己能不能开始操作？
3. **主路径**：是否只保留了第一次成功所需要的动作？
4. **小标题**：是否能够让读者直接判断这里要做什么？
5. **新概念**：第一次出现时，是否给出了当前任务需要的解释？
6. **关键命令**：后面是否写明可以观察的结果？读者是否知道什么结果代表这一步通过？
7. **安全提醒和平台差异**：是否放在相关操作附近？
8. **短排错**：是否只处理当前步骤中能够快速恢复的问题？
9. **复杂故障**：是否已经转到独立的 Troubleshooting 文档？
10. **拓展内容**：是否放在第一次成功之后？
