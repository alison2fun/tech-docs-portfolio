# 从官方资料到开发者文档集

OPT4001 Datasheet 说明器件封装、工作模式、I²C 和结果寄存器；OPT4001YMNEVM User's Guide 说明评估板、软件界面、连接步骤和局部故障。两份资料各自完整，但开发者真正要完成一次采集时，仍然需要在文档之间来回查找。

这次重构没有再做一个虚构器件样本，也没有把两份资料压缩成一篇更短的参考手册。我先确定开发者要完成什么，再回到官方资料中寻找支撑每一步的页码、图号、字段和限制。

## 先确定开发者任务

第一次评估可以拆成四项任务：

1. 连接评估板，并在 EVM GUI 中看到第一组 lux 数据；
2. 理解 PC、母板、coupon board 和 OPT4001YMN 之间的关系；
3. 配置 Continuous 模式，读取结果寄存器并换算 lux；
4. 根据异常现象，判断问题位于 USB、I²C、数据解析还是光学路径。

这个顺序改变了资料出现的位置。首次采集只保留准备、操作、预期结果和最短恢复动作；寄存器字段进入底层读取页面；完整故障判断进入单独的排查页。

## 为什么拆成三条链路

评估系统不能只看通信连接。我把它拆成三条同时工作的链路：

- **控制链路**：EVM GUI → USB → MSP430 → I²C → OPT4001YMN；
- **电气链路**：VDD / GND / SCL / SDA；
- **光学链路**：环境光 → FPCB 开孔 → 朝向 PCB 的感光区域。

这一区分直接影响故障判断。I²C 可以访问器件，只能说明控制和电气链路可能已经建立；如果 coupon board 方向错误或进光开孔被遮挡，lux 响应仍可能异常。这个结论来自系统结构的交叉阅读，尚未通过作者实物验证。

## 第一次成功路径怎样确定

官方 EVM 指南分别给出了硬件连接、COM 端口、GUI 界面、`Continuous` 和 `Start Capture`。我把这些信息重新连接成一条连续路径：

```text
检查 coupon board
→ 连接 USB
→ 确认两个 COM 端口
→ 启动 EVM GUI
→ 选择 Continuous
→ 点击 Start Capture
→ 看到 lux 数值和持续更新的曲线
```

最后两项是可观察的完成标准。它们比“完成配置”更具体，也让读者知道何时可以停止当前任务、何时应该进入故障排查。

## 四处需要跨资料核对的地方

### 封装与接口

OPTMBEVM 的通用接口可见 `ADDR` 和 `INT`，但 OPT4001YMN / PicoStar 本身只有 VDD、GND、SCL 和 SDA。器件能力必须回到当前封装的引脚表确认，不能从母板丝印反推。

### 板卡层级

官方概览从功能上把系统分成母板和 coupon board；物理结构继续展开后，coupon board 又包含 rigid board、flex board 和 OPT4001YMN。两种说法描述的是不同层级，不应互相替代。

### 通信与测量

OPT4001YMN 上电默认处于 Power-down。它仍然可以响应 I²C，却不会持续产生新的测量结果。因此，“能读寄存器”和“已经开始测量”需要分别判断。

### 地址层级

`0x45` 定位 I²C 总线上的器件；`0x00`、`0x01` 和 `0x0A` 等定位器件内部寄存器。文档把两类地址分开说明，避免读者把地址字节和寄存器指针混在同一步骤中。

## 图表和代码怎样保留边界

官方硬件照片直接使用时，图注保留文档名称、Figure 和页码。为解释控制链路、光学路径和寄存器字段而重绘的图，只保留当前任务需要的关系，并明确标为“根据 TI 官方资料重绘”。

参考代码只负责解析已经读取到的 `0x00` 和 `0x01`，不虚构目标 MCU 的 I²C HAL。代码旁边同时写明：尚未编译，也没有经过实物验证。

## 当前完成到哪里

器件型号、封装、板卡关系、工作模式、I²C 地址、结果字段和 lux 公式已经根据 TI 官方资料核对。页面通过本地文档检查和严格构建。

作者目前没有 OPT4001YMNEVM 实物，因此软件安装、USB 枚举、首次采集、参考代码运行和故障复现仍属于待验证内容。资料确认不会被写成作者已经跑通。
