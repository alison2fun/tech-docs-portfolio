# 我如何把作品集从页面堆叠改成文档系统

这个案例记录技术文档作品集的信息架构改版。网站已经有硬件资料、产品文档、API 文档和文档工程项目，但首页、作品、复盘和方法文章的职责混在一起，读者需要自己从许多页面里拼出重点。

改版先解决阅读顺序：从首页确认方向，进入核心作品查看最终交付物，再按需要阅读项目复盘、相关方法和更新记录。最终结果仍使用 MkDocs Material，原有文章 URL 尽量保留，导航和页面分工则按读者任务重新安排。

## 项目背景

作品集的主要读者包括招聘人员、用人经理和技术文档负责人。他们通常先快速浏览，再决定是否打开项目细节，因此入口页需要尽快回答三个问题：候选人做过什么，哪些页面可以作为证据，下一步应当从哪里继续。

网站本身也是一份技术文档。它需要入口、导航、页面分工、版本记录和链接维护，而不能只把做过的页面依次放上去。

## 原始资料与限制

改版使用仓库中已经存在的首页、作品总览、项目文档、案例复盘、方法文章、简历和更新记录。站点继续使用 MkDocs Material、Markdown、Vale 与 GitHub Actions，没有更换主题或另建展示系统。

仓库没有可用于判断招聘转化的访问分析，也没有经过记录的招聘者测试结果。因此，这次只能验证导航、链接、页面层级、构建和响应式表现，不能把页面调整写成已经提高了招聘效果。

## 原页面的问题

问题不在于内容数量不足，而在于页面之间缺少清楚的分工。

- 首页同时承担个人介绍、项目列表、技能和阅读导航，主入口不够集中。
- 多篇作品以平铺页面出现，读者看不出哪些属于同一个项目。
- 最终交付物、项目过程和通用方法使用相近的卡片权重，自己的项目没有被优先展示。
- “案例复盘”和“写作与方法”分成两个一级入口，读者需要在两处来回判断文章类型。
- 一些文章结尾只返回栏目首页，没有接回对应的最终作品或后续方法。

## 我怎样确定优先级

我先处理会影响全站阅读的入口和页面职责，再调整单篇文章。顺序是：首页与核心作品、项目复盘、方法文章、外部文档拆解，最后才是样式细节。

判断标准也保持简单：读者能否先看到最终交付物，能否继续找到过程证据，能否区分已经完成、正在整理和尚未验证的内容。

## 关键取舍

### 保留 MkDocs，重排信息架构

导航、搜索、Markdown 和自动构建仍然适合这个作品集。问题来自内容分工，不需要通过更换技术栈解决。

### 合并复盘和方法入口

“案例复盘”和“写作与方法”都在解释作品背后的判断，但原来被放成两个并列入口。改版后，它们合并为“复盘与方法”：自己的项目复盘优先，从项目中总结的方法和外部文档拆解统一归入写作方法。

### 减少平铺文章

项目复盘改成一组纵向文章列表，完成的文章排在前面，整理中的文章放在最后。方法文章和外部文档拆解使用简洁文字列表，不再用分类卡片重复推荐。

### 保留旧 URL

仓库没有重定向插件。现有文章文件因此继续保留，旧的 `/posts/` 入口和“技术文档作品集为什么需要信息架构”页面改成简短迁移页，不再复制完整正文。

## 修改前后对比

| 检查项 | 修改前 | 修改后 |
| --- | --- | --- |
| 顶部导航 | 案例复盘、写作与方法分别出现 | 合并为复盘与方法 |
| 内容顺序 | 项目复盘、方法和外部拆解权重接近 | 项目复盘 → 写作方法 |
| 推荐内容 | 同一篇复盘在推荐区和列表中重复 | 每篇复盘只出现一次 |
| 方法文章 | 多篇文章以分类卡片平铺 | 直接列出文章标题和摘要 |
| 外部拆解 | 单独占用一个二级栏目 | 作为写作方法的三级分类 |
| 旧入口 | 两个栏目各自承担总览 | 旧 URL 提供迁移说明并指向统一入口 |

## 验证结果

改版后需要同时检查顶部导航、旧 URL、内部链接、严格构建、Vale 和移动端布局。构建与检查结果以本次仓库验收记录为准，不把浏览器中的视觉调整代替链接和构建验证。

## 当前限制

当前结果能够证明页面分工、导航和链接已经按计划重组，不能证明招聘者一定会按照预设顺序阅读，也不能证明改版提高了求职转化。不同屏幕尺寸下的长标题、卡片高度和导航折叠仍需在内容继续增加时复查。
